# NOVA 배포 워크플로 점검 — 기존 PKT 자동 배포 대상 불일치

## 결론

`prototype-nova/nova-front`의 Axios·회원 가입 변경을 `main`에 푸시한 뒤 자동 배포가 시작됐지만, 현재 GitHub Actions는 NOVA가 아닌 과거 PKT 서비스 경로와 HIBOT 운영 인프라를 대상으로 한다. 따라서 이 워크플로를 NOVA 릴리즈에 수동 실행하거나 경로만 바꿔 재시도하면 다른 서비스를 배포·덮어쓸 위험이 있다.

이번 실행은 JAR 빌드 시작 전에 실패했으므로 EC2 서비스, S3 객체, CloudFront cache에는 변경이 없었다.

## PKT Study Fullstack Tauri 릴리즈와의 구분

`tikitaka-note/pkt-study-fullstack`은 NOVA와 독립된 Git 저장소·Tauri 릴리즈 대상이다. 이 저장소의 `v0.1.104` GitHub Release는 2026-09-09에 정상 생성됐다. NOVA 배포 실패는 이 Tauri 릴리즈와 관계가 없으며, Tauri 릴리즈 흐름이나 해당 저장소의 현재 미커밋 변경을 수정 대상으로 삼지 않는다.

## 발생한 실행과 직접 원인

- 푸시 커밋: `3128ab8 feat(front): add axios api client and signup flow`
- GitHub Actions 실행: `Deploy backend` run `34438190166`
- 실패 단계: `Build boot JAR`
- 오류: 작업 디렉터리 `/home/runner/work/sample-pkt-project/sample-pkt-project/sk-pkt-mes-server`가 존재하지 않음

`backend-deploy.yml`은 `working-directory: sk-pkt-mes-server`를 사용하지만, 현재 저장소의 NOVA 백엔드 경로는 `prototype-nova/nova-backend`다. 참조하는 `sk-pkt-mes-server` 디렉터리는 저장소에 없다.

## 프론트 워크플로도 NOVA 대상이 아닌 이유

`frontend-deploy.yml`은 다음 PKT/HIBOT 전용 구성을 사용한다.

```text
working-directory: prac-pkt-react
VITE_API_BASE_URL=https://api.hibot-docu.com/api
aws s3 sync dist/ ... --delete
https://hibot-docu.com 확인
```

하지만 NOVA 프론트는 다음과 다르다.

```text
소스: prototype-nova/nova-front
프레임워크: Next.js
환경 변수: NEXT_PUBLIC_API_BASE_URL
기본 빌드 산출물: .next
```

즉 기존 워크플로가 기대하는 `prac-pkt-react`와 `dist/`는 존재하지 않으며, S3/CloudFront 대상과 HIBOT API URL도 NOVA에 사용할 수 없다.

## 현재 배포 체인

```text
main push
  -> Deploy backend
       -> sk-pkt-mes-server 빌드 시도 (경로 없음, 실패)
  -> Deploy frontend
       -> backend 성공 후에만 시작하므로 skipped
```

모든 `main` 푸시가 이 체인을 시작하므로 NOVA 전용 경로가 만들어지기 전에는 NOVA 프론트 변경도 실패한 PKT 배포 실행을 발생시킨다.

## NOVA 전용 배포를 만들기 전 확정할 항목

1. **운영 대상**: NOVA 전용 도메인, EC2 또는 다른 런타임, systemd 서비스 이름, 데이터베이스를 정한다. HIBOT의 EC2·S3·CloudFront·Secrets를 재사용하지 않는다.
2. **백엔드 배포 경로**: `prototype-nova/nova-backend`에서 JAR를 빌드하고, NOVA 전용 JAR 설치 경로·서비스 이름·헬스 체크 URL을 정한다.
3. **프론트 호스팅 방식**: Next.js 서버 런타임으로 운영할지, `output: "export"`를 명시해 정적 파일로 운영할지 결정한다. 현재 `next.config.ts`는 정적 export 설정이 없으므로 기존 `dist/` S3 동기화 방식과 호환되지 않는다.
4. **환경 변수 계약**: 프론트의 `NEXT_PUBLIC_API_BASE_URL`, 백엔드의 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `SERVER_PORT`, `CORS_ALLOWED_ORIGIN`에 NOVA 전용 값을 등록한다.
5. **GitHub Actions 분리**: NOVA 전용 workflow와 PKT/HIBOT workflow를 분리하고, `paths` 필터로 각 서비스 변경만 해당 배포를 시작하게 한다.
6. **검증과 롤백**: 프론트 URL, API health 또는 OpenAPI URL, CORS origin, 이전 JAR 또는 이전 정적 배포본으로의 복구 절차를 workflow에 포함한다.

## 안전한 다음 작업

NOVA의 운영 도메인·호스팅 방식·전용 Secrets와 배포 대상이 정해진 후에만 `nove-backend`와 `nova-front`용 workflow를 새로 만든다. 기존 `.github/workflows/backend-deploy.yml`, `.github/workflows/frontend-deploy.yml`은 PKT/HIBOT 운영 문서와 연결돼 있으므로 NOVA 릴리즈를 위해 수정하거나 수동 실행하지 않는다.

# Tauri 로컬 SQLite 포함 배포 안전 기준

## 목적과 적용 범위

이 문서는 `pkt-study-fullstack` 온보딩·학습용 Tauri 앱에 로컬 SQLite 기준 DB를 포함해 배포할 때의 안전 기준을 정리한 참고 문서입니다.

현재 앱은 실제 고객 데이터를 다루는 운영형 제품이 아니라 기준 학습 데이터를 동일하게 배포하는 테스트 앱입니다. 이 전제에서는 로컬 DB를 릴리즈에 포함하고, 버전 변경 시 사용자 DB를 패키징된 기준 시드로 동기화하는 구조를 사용할 수 있습니다. `v0.1.43`에서 실제 설치 및 기존 버전 데이터의 업데이트 경로를 검증했습니다.

## 결론

현재 온보딩·학습용 앱 기준으로는 배포 구조와 로컬 DB 포함 방식 모두 사용할 수 있습니다. 다만 다음 조건을 모두 만족해야 안전합니다.

- DB에 실제 고객정보, API 토큰, 개인키, 운영 비밀번호 등 민감정보가 없어야 합니다.
- 릴리즈 전 앱과 개발 서버를 종료하고 WAL 체크포인트를 수행해야 합니다.
- `PRAGMA integrity_check` 결과가 반드시 `ok`여야 합니다.
- `.db-wal`, `.db-shm`은 배포하지 않고 기준 `.db`만 포함해야 합니다.
- 신규 설치와 이전 버전 업데이트 경로를 모두 검증해야 합니다.
- 업데이트 시 사용자 DB는 기준 시드로 교체됩니다. 기존 DB와 WAL·SHM은 백업되지만, 앱에서 사용하던 사용자 수정 데이터는 새 기준 시드로 덮어써집니다.

즉, 현재 테스트 환경에서는 이 방식이 적합하지만 실제 고객 데이터를 보존해야 하는 제품으로 전환할 때는 DB 전체 교체를 중단하고 스키마·데이터 마이그레이션 방식으로 바꿔야 합니다.

## 릴리즈 전 필수 확인

### 1. 실행 프로세스 종료

기준 DB를 사용하는 앱, Next.js 개발 서버, SQLite 관리 도구를 먼저 종료합니다. DB가 열린 상태에서 파일만 복사하면 WAL에 남은 변경이 누락되거나 일관성이 깨질 수 있습니다.

### 2. WAL 체크포인트와 무결성 검사

```bash
cd /Users/terecal/pilot-project/sample-pkt-project/pkt-study-fullstack

sqlite3 .data/pkt-study.db \
  "PRAGMA wal_checkpoint(TRUNCATE); PRAGMA integrity_check;"
```

마지막 결과가 `ok`가 아니면 릴리즈하지 않습니다. 인덱스 오류만 확인된 경우에도 원인을 확인하고 복구한 뒤 다시 전체 무결성 검사를 통과해야 합니다.

### 3. 배포 파일 확인

```bash
git ls-files .data/pkt-study.db
git status --short
find .data -maxdepth 1 -type f -print
```

확인 기준은 다음과 같습니다.

- `.data/pkt-study.db`는 Git에서 추적됩니다.
- `pkt-study.db-wal`, `pkt-study.db-shm`은 Git과 패키징 대상에서 제외됩니다.
- 복구용 `*.before-seed-sync` 파일도 릴리즈에 포함하지 않습니다.
- 릴리즈할 DB의 공간·카테고리·주제·문서 수와 주요 본문을 확인합니다.

### 4. 패키징 결과 재검사

```bash
npm run build:tauri
sqlite3 dist/next/.data/pkt-study.db "PRAGMA integrity_check;"
```

원본 DB뿐 아니라 실제 Tauri 리소스에 복사된 DB도 `ok`인지 확인합니다.

## 설치 및 업데이트 검증

릴리즈 완료는 `latest.json`과 설치 파일 생성만으로 판단하지 않습니다.

### 신규 설치

1. 사용자 데이터가 없는 새 환경에서 앱을 실행합니다.
2. 패키징된 기준 시드가 Tauri `app_data_dir`로 복사되는지 확인합니다.
3. `/api/health`가 HTTP 200을 반환하는지 확인합니다.
4. 메뉴 개수뿐 아니라 문서 본문이 실제로 표시되는지 확인합니다.
5. 사용자 DB의 `PRAGMA integrity_check`가 `ok`인지 확인합니다.

### 이전 버전 업데이트

1. 이전 버전 사용자 DB 복제본과 `-wal`, `-shm`이 있는 상태를 준비합니다.
2. 새 버전을 설치하거나 updater로 갱신합니다.
3. 기존 DB, WAL, SHM이 각각 `.before-seed-sync`로 백업되는지 확인합니다.
4. 이전 WAL·SHM이 새 DB에 재적용되지 않고 새 세션 파일로 생성되는지 확인합니다.
5. `/api/health`, 로그인 화면, 주요 플레이북 본문을 확인합니다.

## `v0.1.43` 이전 장애에서 확인한 사항

이번 장애는 로컬 DB를 포함하는 배포 구조 자체보다 DB 교체 구현에 필요한 보호 절차가 빠져 발생했습니다.

1. 기준 시드의 SQLite 인덱스 손상으로 `SQLITE_CORRUPT`가 발생했습니다.
2. 버전 업데이트 때 DB 본체만 교체하고 이전 `-wal`, `-shm`을 남겨 새 DB에 오래된 WAL이 재적용됐습니다.
3. 앱 번들 내부의 읽기 전용 SQLite 시드를 서버에서 다시 열어 `SQLITE_CANTOPEN`이 발생했습니다.

`v0.1.43`에서는 다음과 같이 보완했습니다.

- 새 DB를 임시 파일에 준비한 뒤 교체합니다.
- 기존 DB, WAL, SHM을 별도로 백업합니다.
- 교체 전에 오래된 WAL과 SHM을 제거합니다.
- 서버는 앱 번들 내부의 읽기 전용 시드를 다시 열지 않습니다.
- 선택적 시드 병합 실패가 전체 Next.js 서버의 HTTP 500으로 번지지 않도록 방어합니다.

## 운영형 제품으로 전환할 때

실제 사용자가 작성한 문서와 이력을 보존해야 하면 현재의 버전별 기준 DB 교체 정책을 그대로 사용하지 않습니다.

- DB 본체 대신 버전별 스키마 마이그레이션을 배포합니다.
- 기준 데이터는 고유 키를 기준으로 필요한 행만 추가하거나 갱신합니다.
- 사용자 문서와 수정 이력은 덮어쓰지 않습니다.
- 마이그레이션 전후 백업, 롤백, 무결성 검사를 자동화합니다.
- 고객정보나 인증정보가 포함된 DB 파일은 GitHub 저장소와 공개 Release에 올리지 않습니다.

## 권장 자동 실패 조건

향후 릴리즈 스크립트나 GitHub Actions에는 다음 조건을 자동 게이트로 추가하는 것이 좋습니다.

- 원본 DB `PRAGMA integrity_check != ok`이면 빌드 실패
- 패키징 DB `PRAGMA integrity_check != ok`이면 빌드 실패
- `.db-wal` 또는 `.db-shm`이 패키징되면 빌드 실패
- 기준 공간·문서 수가 예상값보다 작으면 빌드 실패
- macOS와 Windows 워크플로 중 하나라도 실패하면 릴리즈 완료 처리 금지
- 설치 후 `/api/health`가 HTTP 200이 아니면 배포 검증 실패

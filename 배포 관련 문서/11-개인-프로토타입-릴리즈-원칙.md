# 개인 프로토타입 릴리즈 원칙

## 적용 범위

- NOVA 소스: `prototype-nova/nova-backend`, `prototype-nova/nova-front`
- PKT Study Fullstack Tauri: `tikitaka-note/pkt-study-fullstack`

두 대상은 개인 학습·프로토타입 프로젝트다. 코드 변경의 커밋, 원격 저장소 푸시, GitHub Release 생성에는 별도 승인 단계나 변경 심의 절차를 두지 않는다.

## 공통 작업 순서

1. 변경 파일과 `git diff --check`를 확인한다.
2. 대상별 테스트와 빌드를 실행한다.
3. 변경 목적별로 커밋한다.
4. 원격 기본 브랜치 또는 작업 브랜치에 푸시한다.
5. 릴리즈 대상이면 버전을 올리고 태그·Release·산출물을 확인한다.

개인 프로젝트라도 다른 서비스의 인프라나 비밀값을 덮어쓰는 작업은 하지 않는다. 특히 HIBOT/PKT 운영용 워크플로를 NOVA 릴리즈에 재사용하지 않는다.

## NOVA

NOVA 프론트와 백엔드는 `sample-pkt-project` 저장소의 같은 변경 집합으로 관리한다. API 계약이 바뀌면 백엔드 테스트를 먼저 통과시키고, 프론트 lint·build를 통과시킨 뒤 함께 커밋·푸시한다.

현재 저장소의 기존 GitHub Actions 배포 워크플로는 과거 PKT/HIBOT 경로와 인프라를 대상으로 한다. 따라서 NOVA 변경을 푸시하는 것은 허용하지만, 그 워크플로를 NOVA 배포 목적으로 실행하지 않는다. NOVA 전용 호스팅과 workflow가 준비되기 전의 “릴리즈”는 소스 커밋·푸시와 검증 완료를 뜻한다.

## PKT Study Fullstack Tauri

Tauri 릴리즈는 `tikitaka-note/pkt-study-fullstack`에서 수행한다. 문서·메뉴 변경은 `.data/pkt-study.db` 기준 시드에 포함되므로, 앱 코드와 시드 DB를 같은 릴리즈에 넣는다.

- 현재 버전보다 패치 버전을 하나 올리는 것을 기본으로 한다. 기능 호환성이 깨지는 변경은 minor 또는 major 버전으로 올린다.
- `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, 화면 버전을 일치시킨다.
- 새 설치용 시드와 기존 사용자 DB 동기화 결과를 확인한다.
- macOS는 Developer ID 서명·공증·staple·Gatekeeper 검증을 거친 DMG를 Release에 올린다.
- Windows 설치 파일이 필요한 경우에만 Windows workflow를 실행하고 Release 자산을 확인한다.

개인 프로젝트라는 이유로 SQLite 시드 검증, 버전 일치, 서명 키 보호를 생략하지 않는다. 이 항목들은 승인 절차가 아니라 설치 가능한 앱을 만들기 위한 기술 조건이다.

# 공통 UI 갤러리 고도화 아이디어 및 계획

## 1. 목표

공통 UI를 단순한 디자인 참고용 문서 모음이 아니라, 실제로 바로 가져다 쓸 수 있는 컴포넌트 갤러리로 운영한다.

- 실제 컴포넌트 렌더링 결과와 소스를 항상 같은 기준으로 제공한다.
- 일반 노트와 공통 UI 갤러리를 시각적·기능적으로 구분한다.
- 기본값은 보편적인 Light 모드로 두고, 필요한 경우 Dark·반응형·접근성 상태를 함께 확인한다.
- 메뉴와 갤러리 파일은 시스템 자산으로 취급하여 실수로 삭제되지 않게 한다.

## 2. 핵심 아이디어

### 2.1 공통 UI와 문서 노트의 역할 분리

`공통 UI`는 디자인 설명보다 실제 사용 가능한 컴포넌트와 변형을 보여주는 영역으로 정의한다. 구현 원리, 선택 기준, 트러블슈팅, 학습 메모는 일반 노트에 둔다.

- 공통 UI 갤러리: Button, Input, Form, Tabs, Breadcrumb, Pagination, Layout, Interaction 등
- 일반 노트: CSS 원리, 접근성 설명, 상태 관리 방법, 라이브러리 비교, 구현 회고
- 갤러리 문서: 설명 + 실제 렌더링 + 소스 보기 + 사용 예시

### 2.2 하나의 컴포넌트 정의에서 렌더링과 소스 생성

현재처럼 `mode`에 따라 미리보기 JSX를 직접 분기하는 방식은 빠른 시제품에는 적합하지만, 컴포넌트가 늘어나면 화면과 소스가 어긋날 수 있다.

향후에는 컴포넌트 정의를 한 곳에서 관리한다.

```ts
type ComponentExample = {
  id: string;
  title: string;
  description?: string;
  source: {
    tsx: string;
    css?: string;
  };
  render: (props: Record<string, unknown>) => React.ReactNode;
  controls?: ControlDefinition[];
};
```

동일한 정의를 다음 두 곳에서 사용한다.

1. 미리보기 렌더러: 실제 인터랙션이 동작하는 컴포넌트 표시
2. 소스 패널: 렌더러와 일치하는 TSX/Tailwind/CSS 코드 표시

초기에는 안전한 로컬 레지스트리 방식으로 시작하고, 임의의 사용자 코드 실행은 허용하지 않는다. Tailwind 예시는 정적 클래스와 제한된 props만 허용하는 샌드박스 컴포넌트로 관리한다.

### 2.3 갤러리 문서 표준

각 갤러리 문서는 다음 순서를 기본으로 한다.

1. 컴포넌트 목적
2. 실제 컴포넌트 미리보기
3. 주요 변형과 상태
4. 사용 가능한 props 또는 설정값
5. TSX 및 스타일 소스
6. 사용 시 주의점
7. 완료 기준

미리보기에는 `실제 컴포넌트` 표시를 붙이고, 하드코딩된 설명 그림과 구분한다.

### 2.4 시각적 구분

공통 UI 갤러리는 일반 노트와 구분되도록 다음 표시를 사용한다.

- 메뉴 영역명: `공통 UI`
- 문서 상단 배지: `실제 컴포넌트`, `시스템`, `고정 갤러리`
- 컴포넌트 문서의 파란색 경로와 소스 보기 버튼
- 시스템 메뉴·1차·2차 본문은 잠금 상태로 표시

잠금은 학습 데이터와 실제 파일 연동 관계를 보호하기 위한 것이며, 수정이 필요한 경우 새 문서나 버전 문서를 추가하는 방식으로 운영한다.

## 4. 단계별 실행 계획

### 1단계 — 현재 갤러리 안정화

- 메뉴명과 1차·2차 구조를 위 제안에 맞춰 정리한다.
- 시스템 갤러리의 삭제·이동·본문 삭제를 차단한다.
- Light 기본값, 상태 배지, 실제 컴포넌트 표시를 공통 규칙으로 확정한다.
- 미리보기 패널의 높이·overflow·dropdown 영역을 점검한다.
- 작은 화면에서도 콘텐츠가 잘리지 않도록 세로 스크롤을 보장한다.

### 2단계 — 소스와 화면 매칭

- 컴포넌트 레지스트리를 만들고 `id`, `render`, `source`, `controls`를 한 곳에 둔다.
- 소스 맵의 수동 문자열을 레지스트리 또는 실제 파일에서 생성하도록 바꾼다.
- TSX와 CSS뿐 아니라 Tailwind 클래스가 포함된 TSX도 표시할 수 있게 한다.
- 화면에서 선택한 variant·size·state가 소스 예시와 일치하는지 검증한다.
- 파일을 찾지 못했을 때는 빈 코드 대신 원인과 경로를 표시한다.

### 3단계 — 바로 쓸 수 있는 컴포넌트화

- Button, Input, Select부터 공통 props와 상태 모델을 정의한다.
- Form은 로그인·회원가입·검색 등 실제 시나리오 단위로 만든다.
- Tabs·Dropdown·Accordion은 키보드 조작, 포커스, 바깥 클릭, overflow를 포함한다.
- Layout은 Grid·Flex·반응형을 실제 화면 폭에서 확인할 수 있게 한다.
- 각 예시는 복사 가능한 TSX와 필요한 스타일을 제공한다.

### 4단계 — 품질·운영 체계

- 모든 컴포넌트에 기본·hover·focus·disabled·error 상태를 정의한다.
- Light를 기본으로 하고 Dark는 별도 변형으로 제공한다.
- 접근성 점검 항목과 반응형 점검 항목을 문서 완료 기준에 포함한다.
- 갤러리 문서 버전을 관리하고 기존 예시를 함부로 덮어쓰지 않는다.
- 릴리즈 전 렌더링, 소스 보기, 복사, 업데이트 경로를 함께 확인한다.

## 5. 우선순위

1. 소스와 렌더링 불일치 제거
2. 갤러리 자산 보호 및 메뉴 구조 정리
3. Button·Input·Select 기반 컴포넌트 레지스트리
4. Form UI 시나리오 확장
5. Layout·Interaction·State의 실제 동작 강화
6. 접근성·Dark·반응형 품질 보강

## 6. 완료 기준

- 문서에서 보이는 컴포넌트와 소스가 동일한 구현을 가리킨다.
- variant나 상태를 변경하면 미리보기와 코드 설명이 함께 바뀐다.
- 갤러리 문서는 실제 컴포넌트 여부와 기본 테마를 명확히 표시한다.
- 시스템 메뉴와 보호 대상 본문은 일반 삭제 흐름으로 제거되지 않는다.
- 좁은 패널에서도 드롭다운·코드·미리보기 내용이 잘리지 않는다.
- 사용자는 문서의 소스를 복사해 별도 화면에 바로 적용할 수 있다.

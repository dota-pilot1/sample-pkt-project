하위 문서 순서 바꾸기 실패 이유

하위 문서를 끌어 놓으면 화면에서는 이동했지만 번호가 바뀌지 않았고, 다른 메뉴에 갔다 오거나 새로고침하면 원래 순서로 돌아왔다.

대상 저장소: tikitaka-note/pkt-study-fullstack · 기능: 제품 설계 노트의 본문·하위 문서 정렬

최종 원인: @dnd-kit/react의 낙관적 정렬이 DOM을 먼저 이동시킨 뒤 드롭 대상을 자기 자신으로 돌려주는데, 기존 코드가 source.id === target.id이면 변경이 없다고 판단해 종료했다. 따라서 화면만 잠깐 움직이고 React 상태, API 요청, DB 순서는 모두 그대로였다.

1. 재현 증상과 그 의미

화면 순서

1.1 → 1.3 → 1.2처럼 카드 위치는 이동했다. 이 이동은 React 데이터가 바뀐 결과가 아니라 dnd-kit 플러그인이 DOM을 낙관적으로 이동시킨 결과였다.

번호 표시

카드의 번호는 여전히 1.1 / 1.3 / 1.2였다. 번호는 문서 배열의 실제 순서에서 계산하므로 React Query 캐시가 갱신되지 않았다는 증거다.

네트워크

드롭 후 reorder POST가 발생하지 않았다. 화면 이동만 보고 저장 성공으로 판단하면 안 되는 핵심 단서였다.

재조회

다른 메뉴에 갔다 오거나 새로고침하면 원래 순서로 돌아왔다. 서버와 DB의 orderIdx가 한 번도 변경되지 않았기 때문이다.

2. 정상적인 순서 변경 흐름

드래그 정렬은 화면 위치 하나만 바꾸는 기능이 아니다. 아래 네 단계가 모두 완료돼야 실제로 저장된 것이다.

3. 실제 원인

드롭 대상 ID가 아니라 sortable 인덱스가 진짜 이동 정보였다. OptimisticSortingPlugin이 화면 요소를 먼저 재배치한 뒤에는 target.id가 이동한 문서 자신의 ID로 관찰될 수 있다. 이때 source.id === target.id는 “이동 없음”을 뜻하지 않는다. 이동 여부는 source.initialIndex와 source.index를 비교해야 한다.

수정한 드롭 해석 함수

export function documentOrderAfterDrop(
  documents: PlaybookDocumentSummary[],
  event: DragEndEvent,
) {
  const { source, target } = event.operation;
  if (event.canceled || !target || !isSortable(source)) return null;

  const document = documents.find((item) => item.id === source.id);
  if (!document) return null;

  const group = documentSortableGroup(document);
  if (source.initialGroup !== group || source.group !== group) return null;

  // 낙관적 정렬 뒤에는 target이 source 자신이어도 인덱스는 달라질 수 있다.
  const from = source.initialIndex;
  const to = source.index;
  const siblings = documents.filter(
    (item) => item.parentId === document.parentId,
  );

  if (
    from === to ||
    siblings[from]?.id !== document.id ||
    !Number.isInteger(to) ||
    to < 0 ||
    to >= siblings.length
  ) {
    return null;
  }

  return {
    ids: arrayMove(siblings, from, to).map((item) => item.id),
    parentId: document.parentId,
  };
}

4. 실제 원인과 별개였던 문제들

디버깅 중 세 문제가 겹쳤다. 모두 고쳐야 했지만, 각각의 역할을 구분하지 않아 “API는 되는데 화면은 왜 그대로인가”라는 혼란이 생겼다.

1. 화면 이벤트

최종 UI 원인. 드롭 핸들러가 같은 ID를 이동 없음으로 처리해 mutation을 호출하지 않았다. 네트워크 요청 자체가 없었다.

2. API 경로

필수 보완. LLM용 reorder API와 별개로 일반 UI가 호출하는 /api/hospital-playbook/topics/{topicId}/documents/reorder 경로가 필요했다.

3. 개발 서버

검증 방해 요인. 실행 중인 Next 개발 서버가 이전 모듈을 잡고 있어 reorderDocuments is not a function을 냈다. 재시작 시에는 기존 4300 포트 프로세스 때문에 EADDRINUSE도 발생했다.

왜 API 직접 호출만으로는 해결됐다고 볼 수 없었나

인증된 상태로 reorder API를 직접 호출했을 때 204가 반환되고 DB 저장도 성공했다. 이것은 서버 계약이 정상이라는 뜻일 뿐, 실제 드래그 UI가 그 API를 호출한다는 증거는 아니다. 브라우저에서 드롭한 뒤 요청 목록이 비어 있었기 때문에 프론트 이벤트 경로를 다시 추적해야 했다.

5. 수정 구조

동일 부모 그룹 제한

topicId + parentId로 sortable group을 만들었다. 같은 부모 아래 문서끼리만 순서를 바꿀 수 있다.

인덱스로 이동 계산

initialIndex와 현재 index로 이동 전후를 계산한다. target ID 동일 여부는 무시한다.

공통 함수 사용

목록 화면과 전체 문서 페이지가 같은 documentOrderAfterDrop()을 사용해 동작 차이를 없앴다.

낙관적 캐시 갱신

서버 응답 전 React Query 캐시의 배열과 orderIdx를 함께 바꿔 카드 번호도 즉시 다시 계산한다.

실패 시 재조회

저장 실패 시 서버 데이터를 다시 조회하고 오류 토스트를 보여준다. 성공 토스트는 잦은 정렬 작업을 방해하므로 생략했다.

펼침 상태 유지

전체 문서 페이지에서 재정렬 후에도 부모 문서의 펼침 상태가 유지되도록 상태 동기화를 보완했다.

6. 서버에서 순서를 저장하는 기준

클라이언트는 이동한 한 건만 보내지 않고, 같은 부모를 가진 형제 문서 ID 전체를 원하는 순서대로 보낸다. 서버는 누락·혼입 여부를 검증한 뒤 배열 위치를 새 orderIdx로 저장한다.

POST /api/hospital-playbook/topics/2030/documents/reorder
Content-Type: application/json

{
  "ids": [437, 439, 438],
  "parentId": 431
}
  • ids는 해당 부모의 전체 자식 ID를 중복 없이 포함해야 한다.
  • 다른 부모의 문서가 섞이거나 일부가 빠지면 400으로 거절한다.
  • 검증을 통과하면 하나의 DB 트랜잭션에서 0, 1, 2...로 다시 저장한다.
  • 성공 응답은 본문 없는 204 No Content다.

8. 재발 방지를 위한 디버깅 순서

  1. 화면 이동과 상태 변경을 구분한다. DnD 라이브러리는 DOM을 먼저 움직일 수 있으므로 번호나 React DevTools 상태도 같이 본다.
  2. Network를 가장 먼저 본다. 요청이 없으면 서버·DB를 더 파기 전에 이벤트 핸들러의 조기 종료 조건을 확인한다.
  3. 드롭 이벤트 원문을 기록한다. source.id, target.id, initialIndex, index, group을 한 번에 비교한다.
  4. 직접 API 테스트와 UI 통합 테스트를 분리한다. API 204는 서버만 통과했다는 뜻이다. 실제 드래그가 요청을 만들었는지 별도로 검증한다.
  5. 저장 결과는 재조회로 확인한다. 메뉴 재진입과 새로고침을 통과해야 영속화가 끝난 것이다.
  6. 개발 서버 상태를 의심한다. 새 export가 함수가 아니라고 나오면 실행 중인 프로세스와 포트를 확인하고 단일 서버로 재시작한다.
완료 판정 기준: “드래그되어 보인다”가 아니라 위치 변경 + 번호 재계산 + POST 발생 + DB 반영 + 재진입 유지가 모두 성공해야 한다.
이 문서는 하위 문서 정렬 장애의 재현, 원인, 수정, 검증을 현재 구현 기준으로 정리한 디버깅 기록이다.

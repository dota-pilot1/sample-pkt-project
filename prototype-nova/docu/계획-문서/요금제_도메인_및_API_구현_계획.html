NOVA · Part 1

요금제 도메인 및 API 구현 계획

첫 업무 흐름인 요금제 생성 → 판매 가능을 완성하기 위한 백엔드 설계 계획이다. 가입·주문·개통은 이번 구현의 소비자가 아니라 다음 단계의 확장 지점으로만 남긴다.

1. 이번에 만들 것

이번에 함

요금제 종류를 기준정보로 관리하고, 요금제를 만들고, 고치고, 목록에서 찾고, 판매를 시작하거나 멈춘다. 누가 바꿨는지도 간단히 남긴다.

나중에 함

고객 가입, 주문, 개통, 할인 계산은 아직 만들지 않는다. 지금은 그 기능들이 나중에 요금제를 골라 쓸 수 있게만 준비한다.

한 줄로: 요금제는 나중에 고객이 가입할 때 고르는 상품이다. 그래서 함부로 지우지 않고, 더 팔지 않을 때는 “판매 중지”로 바꾼다.

2. 요금제 사용 규칙

1. 작성 중→2. 판매 시작→3. 판매 중지→4. 완전 종료
  • 요금제 번호는 하나뿐이다. 한 번 만든 번호는 바꾸지 않고, 다른 요금제와 겹치면 안 된다.
  • 필수 내용을 다 채운 뒤에만 판매를 시작한다. 이름, 종류, 한 달 요금, 판매 시작일이 있어야 한다.
  • 판매 중지하면 새 고객은 고를 수 없다. 이미 쓰는 고객을 계속 유지할지는 가입 기능을 만들 때 정한다.
  • 웬만하면 지우지 않는다. 잘못 만든 것은 아직 판매 전일 때만 지우고, 이미 판매했다면 “판매 중지”로 남긴다.
  • 돈은 원 단위로 정확하게 저장한다. 예: 11,000원. 소수점 계산 때문에 10,999.999원이 되는 문제를 막는다.

4. DB 그림 (ERD)

표는 세 개다. 요금제 종류를 먼저 만들고, 요금제는 그 종류를 하나 고른다. 요금제가 바뀔 때마다 변경 기록을 하나씩 남긴다.

erDiagram
    PLAN_CATEGORIES ||--o{ PLANS : "여러 요금제로 나뉨"
    PLANS ||--o{ PLAN_CHANGE_HISTORIES : "변경 기록을 남김"

    PLAN_CATEGORIES {
        bigint id PK "종류 번호"
        varchar code UK "종류 코드"
        varchar name "화면에 보일 이름"
        boolean active "사용 가능 여부"
        int sort_order "표시 순서"
    }
    PLANS {
        bigint id PK "요금제 번호"
        bigint category_id FK "어떤 종류인지"
        varchar plan_code UK "화면에 보이는 코드"
        varchar name "요금제 이름"
        bigint monthly_fee "한 달 요금"
        varchar sales_status "판매 상태"
        datetime sale_start_at "판매 시작일"
        datetime sale_end_at "판매 종료일"
    }
    PLAN_CHANGE_HISTORIES {
        bigint id PK "기록 번호"
        bigint plan_id FK "어떤 요금제인지"
        varchar action "무엇을 했는지"
        varchar changed_by "바꾼 사람"
        datetime changed_at "바꾼 시간"
    }

1 ── ∞ 뜻: 종류 하나에는 여러 요금제가 들어갈 수 있고, 요금제 하나에는 변경 기록이 여러 개 붙을 수 있다. 판매 상태는 지금은 plans 안의 값으로 둔다.

5. 패키지와 계층 설계

프론트 화면
↓
PlanController · 요청을 받음
↓
PlanService · 해야 할 일을 순서대로 처리
↓
Plan · 규칙 확인
PlanRepository · DB에 저장·조회
변경 이력 저장

plan/presentation

프론트가 보낸 요청을 받는 곳. 입력값이 빠지지 않았는지 먼저 확인한다.

plan/application

“요금제 만들기”, “판매 시작하기”처럼 해야 할 일을 순서대로 처리하는 곳.

plan/domain

요금제 자체와 판매 규칙을 두는 곳. “이 상태에서는 판매 시작 불가”를 여기서 막는다.

plan/infrastructure

DB에 저장하고 꺼내오는 곳. 나머지 코드가 DB 방식에 덜 묶이게 한다.

7. 구현 순서

1

요금제 운영 규칙표 만들기

코드를 아직 쓰지 않는다. 먼저 “언제 판매 시작을 누를 수 있는지”, “판매 중지 뒤 다시 팔 수 있는지”, “잘못 만든 요금제를 지울 수 있는지”를 표로 정한다. 같이 확정할 것은 상태 변경 순서, 필수 입력값, 요금제 코드 형식·중복 금지다. 이 표가 이후 DB·API·테스트의 기준이 된다.

2

도메인과 DB 스키마 구현

plan_categories, plans, plan_change_histories를 만들고, 요금제 생성·수정·상태 변경 규칙이 제대로 막히는지 테스트한다.

3

유스케이스와 목록 조회 구현

명령 API부터 만든 뒤, TanStack Table이 바로 소비할 수 있는 서버 페이징·검색·정렬 응답을 구현한다.

4

인증·권한과 감사 보강

초기에는 관리자만 변경 가능하게 두고, 변경자 식별과 이력을 연결한다. 역할 세분화는 이후 인증·인가 리뷰 단계에서 진행한다.

5

프론트 연결 및 계약 검증

목록 → 생성 → 수정 → 판매 상태 변경 → 이력 조회를 하나의 사용자 흐름으로 검증한다. 대량 데이터와 가상화는 실제 페이징 한계가 확인된 뒤 검토한다.

8. 완료 조건

  • 완료 요금제를 DRAFT로 만들고 필수 조건을 만족할 때만 ON_SALE로 바꿀 수 있다.
  • 완료 코드 중복, 잘못된 상태 전이, 잘못된 금액·날짜 입력이 일관된 오류 응답으로 막힌다.
  • 완료 프론트 그리드가 서버 검색·정렬·페이지네이션을 사용한다.
  • 다음 단계 가입·주문이 실제 Plan ID와 판매 상태를 참조한다.
  • 다음 단계 역할별 상태 변경 권한과 승인 워크플로를 도입한다.

# MES 학습 노트 작성법

이 폴더의 문서가 MES 학습 노트 작성의 기준이다.

- 이 문서: 계층·내용·Lexical 구조에 대한 규칙
- `본문 형식 샘플.md`: 본문 문서의 화면 구조를 고정하는 예시
- `하위 문서 형식 샘플.md`: TODO 하위 문서와 Step의 화면 구조를 고정하는 예시
- `노트 작업 관련 공개 api for llm.md`: 문서 조회·저장·수정·삭제 API와 작업 순서

규칙과 샘플이 다르면 규칙을 우선하지 말고, 먼저 이 문서와 샘플을 함께 갱신한 뒤 작업한다. 샘플은 설명용 Markdown이 아니라, 최종 화면에서 보여야 하는 순서와 블록 경계를 보여주는 기준 예시다.

이 문서는 `pkt-study-tauri`의 개발 학습 노트를 작성할 때 참고하는 기준 문서다.

앱의 노트 구조는 다음 3단계로 유지한다.

```text
1차 영역(Category)
└── 2차 주제(Topic)
    └── 문서(Document)
```

## 1. 1차 영역 작성 기준

1차 영역은 기술 또는 학습 목적이 크게 달라지는 단위로 나눈다. 너무 많은 영역을 만들지 말고, 관련 주제가 3개 이상 쌓일 때 분리한다.

현재 Component Recipes의 기본 영역은 다음과 같다.

```text
기본 컴포넌트
```

향후 필요할 때만 다음과 같이 영역을 추가한다.

```text
컴포넌트 조합
MES 업무 화면
폐쇄망 운영
```

## 2. 2차 주제 작성 기준

2차 주제는 실제로 재사용할 컴포넌트 하나 또는 밀접한 컴포넌트 묶음으로 만든다.

좋은 예:

```text
기본 컴포넌트
├── Button
├── Input
├── Select
├── Checkbox·Radio·Switch
├── Modal·Drawer
├── Table
├── Badge·Status
├── Tabs·Pagination
├── Loading·Empty·Error
└── Layout·Toolbar
```

피해야 할 예:

```text
기본 컴포넌트 모음
프론트엔드 이것저것
컴포넌트 관련 참고사항
```

범위가 너무 넓은 이름은 문서가 쌓일수록 찾기 어려워진다.

## 3. 문서 제목 작성 기준

하나의 문서는 하나의 학습 또는 구현 목적만 다룬다. 제목만 보아도 문서의 결과물을 알 수 있어야 한다.

권장 제목 형식:

```text
[컴포넌트명] 제조법 — [핵심 목적]
[컴포넌트명] Props와 상태 설계
[컴포넌트명] PKT 적용 예시
[컴포넌트명] 테스트 체크리스트
```

Button 예시:

```text
Button 컴포넌트 제조법 — 폐쇄망 조립형
Button Props와 상태 설계
Button PKT MES 적용 예시
Button 테스트 체크리스트
```

## 4. 계획 문서와 하위 구현 문서의 계층

구현 규모가 있는 주제는 하나의 긴 문서에 모든 내용을 몰아넣지 않고, 상위 계획 문서와 TODO·Step 하위 문서로 나눈다.

```text
2차 주제
├── TODO 1 본문
│   ├── API 구현 하위 문서
│   │   └── 본문에 Step 1~N 구현 과정 작성
│   └── Front 구현 하위 문서
│       └── 본문에 Step 1~N 구현 과정 작성
├── TODO 2 본문
├── TODO 3 본문
├── TODO 4 본문
└── TODO N 본문
```

상위 문서 본문에 TODO 1~N의 계획을 먼저 작성하고, 각 TODO는 상위 문서의 하위 문서 하나로 만든다. TODO 하위 문서의 본문 안에서 Step 1~N을 순서대로 진행한다. Step을 별도 문서 계층으로 다시 만들지 않는 것을 기본으로 한다. TODO와 Step의 개수는 고정하지 않는다. 작업의 범위와 의존성에 따라 조절하되, 제목만 늘리기 위해 인위적으로 쪼개지 않는다. 작은 작업은 TODO 1~2개와 Step 2~3개로 충분하고, 서버·프론트·DB·테스트가 함께 필요한 작업은 TODO 3~6개, 각 TODO의 Step 3~10개를 기준으로 삼되 실제 의미 있는 작업 단위에 맞춘다.

### 상위 계획 문서 본문 기준

TODO 본문 문서는 구현 코드를 모아두는 문서가 아니라 해당 기능의 방향과 완료 기준을 결정하는 문서다. 풀스택 기능을 API와 Front로 나눌 필요가 있으면 TODO 본문 아래에 구현 하위 문서를 둔다. 다음 순서를 기본으로 한다.

1. h1 제목과 TODO 목표
2. 전체 목표를 설명하는 quote
3. 구현 범위와 제외 범위
4. API·Front 하위 문서와 결과물
5. 선행 조건과 후행 작업
6. TODO 완료 조건과 검증 계획

상위 문서에는 아직 구현하지 않은 확정 전 API 경로, 응답 예시, 존재하지 않는 파일 경로를 단정해서 쓰지 않는다. 설계 결정이 필요한 내용은 결정할 항목으로 기록하고, 구현이 완료된 뒤 실제 조회 결과와 파일 위치를 갱신한다.

### TODO 본문 작성 기준

TODO는 상위 계획 문서의 본문 안에서 하나의 계획 항목으로 작성한다. 다른 TODO의 내용을 반복하지 말고, 해당 목표의 결과물·선행 조건·하위 Step 범위를 요약한다.

1. h1 TODO 제목
2. TODO의 목적과 기대 결과
3. TODO에 포함되는 Step 1~N 목록
4. TODO 간 선행·후행 관계
5. TODO 완료 조건

TODO 본문이 계획 단계라면 확정되지 않은 API 경로·응답·파일 경로를 단정하지 않는다. 구현이 완료된 뒤 실제 조회 결과만 해당 TODO 본문과 API·Front 하위 문서에 반영한다.

### TODO 하위 문서 본문과 Step 진행 기준

TODO 하위 문서는 상위 계획 문서의 직접 하위 문서로 만든다. 하위 문서 하나가 TODO 하나를 담당하며, 본문 안에 Step 1~N을 순서대로 작성한다. 하나의 Step은 하나의 구체적인 구현·분석·검증 단위만 다룬다. Step 하나에 여러 독립 작업을 섞지 않으며, 다음 Step이 무엇을 이어받는지 알 수 있게 작성한다.

1. h1 TODO 제목과 전체 목표
2. TODO 목표를 설명하는 quote
3. Step 1~N h2 제목과 각 단계별 quote
4. 선행 조건과 확인할 파일·데이터
5. Step별 작업 파일 경로
6. 구현 완료 시 이해 가능한 단위의 실제 코드 블록
7. 필요한 경우에만 설계 포인트·주의사항
8. 실제 테스트·조회·화면 확인을 실행한 경우에만 검증 결과
9. 다음 Step으로 넘기는 상태와 주의사항

구현이 끝난 Step에는 실제 변경 파일의 절대 경로 또는 저장소 기준 경로와, 독자가 흐름을 파악할 수 있는 함수·훅·컴포넌트·설정 단위의 실제 코드 블록을 기록한다. 단순히 몇 줄만 떼어낸 부분 코드나 설명용 `...`를 넣지 않는다. 여러 파일을 바꿨다면 파일별 책임을 구분하고 각 파일의 핵심 구현 단위를 기록한다. 계획 단계의 Step에는 아직 존재하지 않는 파일의 코드를 지어내지 않는다. 파일 생성이 확정된 경우에만 `구현 예정 경로`로 표시하고, 아직 결정되지 않은 경로는 확인할 영역으로 남긴다. TODO 하위 문서가 길어지더라도 하나의 TODO 목적을 유지하고, 목적이 달라지면 다음 TODO 하위 문서로 분리한다. Step은 별도 `parentId` 문서로 만들지 않고 TODO 하위 문서 본문 안에서 진행한다.

Step별 구현 기록은 다음 형태를 기본으로 한다.

```text
Step N. [작업명]
목적: 이번 단계에서 완료할 한 가지 결과
파일: 실제 변경 파일 경로
코드: 이해 가능한 실제 구현 단위만 독립 code 블록으로 기록
주의사항: 필요한 경우에만 비자명한 설계 판단을 기록
검증: 실제 테스트·조회·화면 확인을 실행한 경우에만 명령과 결과를 기록
```

`주의사항`과 `검증`은 모든 Step에 강제하지 않는다. 코드와 Step 설명만으로 충분한 단순 구현은 생략한다. 검증은 TODO 마지막 Step 또는 전체 계획 문서의 완료 기준에 모아도 된다.

## 5. 컴포넌트 문서의 본문 순서

컴포넌트 문서는 아래 순서를 기본 템플릿으로 사용한다.

1. 목적
2. 사용 시나리오
3. 설계 규칙
4. Props와 상태
5. 코드 블록
6. PKT MES 적용 방법
7. 테스트 체크리스트
8. 확장 또는 주의사항

짧은 문서라도 최소한 목적, 설계 규칙, 코드 블록은 포함한다.

### 본문 줄바꿈과 화면 가독성

일반 설명 문장은 문장마다 임의로 줄을 바꾸지 않고, 화면 너비에 따라 자연스럽게 흐르도록 작성한다. 문장 사이의 강제 줄바꿈을 줄이면 넓은 화면에서 내용이 끊기지 않고 한눈에 읽힌다. 섹션 제목은 배경 없는 제목으로 두고, 제목에 속한 본문 paragraph·list 전체는 하나의 quote 배경으로 묶으며, 코드 블록은 별도 코드 박스로 표시한다.

다음 기준을 적용한다.

- 하나의 생각은 하나의 문단으로 묶고, 문장마다 줄바꿈하지 않는다.
- Lexical root는 children, direction, format, indent, type: "root", version을 포함한다.
- 새로운 주제·단계·조건으로 넘어갈 때 소제목을 사용한다. Lexical에서는 `heading` 노드 다음에 제목에 속한 본문 paragraph·list 전체를 하나의 `quote` 노드로 묶고, 파일 경로·코드는 quote 밖의 독립 `code` 블록으로 배치한다. 다음 섹션 전에는 `children: []`인 빈 paragraph 2개를 둔다.
- 순서·비교·체크 항목처럼 구조가 중요한 내용은 하나의 `list` 노드 안에 `listitem`을 묶어 작성한다. 목록 항목 사이에는 빈 paragraph를 넣지 않는다.
- 섹션 사이의 의도적인 호흡은 항상 `children: []`인 빈 paragraph 2개로 표현하며 CSS 여백에 의존하지 않는다.
- 코드, JSON, 명령어, 파일 경로처럼 줄바꿈 자체가 의미를 갖는 내용은 코드 블록 안에서 원래 줄 구조를 유지한다.
- 코드 블록은 type: "code"이며 children 안에 type: "code-highlight" 노드를 둔다. 파일 경로 블록은 language를 `text`, 실제 코드는 파일에 맞는 `java`, `typescript`, `tsx`, `bash`, `json` 등으로 지정한다. `code-highlight.text`는 자식 노드 type과 저장 호환 표기일 뿐, 실제 코드의 문법 하이라이트 언어로 사용하지 않는다.
- Step 내부의 파일·코드·주의사항·검증 묶음은 같은 간격 규칙을 사용한다. 각 code 블록 뒤에는 빈 paragraph 1개를 두고, 다음 Step 전에는 빈 paragraph 2개를 둔다. 파일·코드 라벨과 바로 아래 code 블록 사이에는 빈 paragraph를 넣지 않는다.
- 소스 코드에는 0-based/1-based 변환, 인증 경계, fallback, 페이지 경계 보정처럼 코드만 읽어서는 의도가 불분명한 주요 함수 위에 짧은 주석을 둔다. 모든 함수에 형식적인 주석을 반복하지 않는다.
- TypeScript에서는 서버 응답 계약, 화면·도메인 모델, 변환표, 페이지 응답처럼 역할이나 변환 경계가 있는 주요 타입·상수 위에 한 줄 주석을 둔다. `string`, `number` 필드마다 주석을 반복하지 않으며, 타입명·폴더명만으로 역할이 명확한 단순 타입에는 생략할 수 있다.
- 본문을 한 줄로 붙이는 것은 전송용 문자열을 만들 때의 규칙이 아니라 화면에 표시되는 학습 문서의 규칙과 구분한다.

## 6. 코드 블록 작성 기준

코드는 본문에 일반 텍스트로 붙이지 말고 반드시 편집기의 코드 블록으로 작성한다.

```tsx
type ButtonVariant = 'primary' | 'secondary' | 'ghost' | 'danger';
type ButtonSize = 'sm' | 'md' | 'lg';

type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: ButtonVariant;
  size?: ButtonSize;
  loading?: boolean;
  children: React.ReactNode;
};

export function Button({
  variant = 'primary',
  size = 'md',
  loading = false,
  disabled,
  children,
  ...props
}: ButtonProps) {
  return (
    <button
      type="button"
      disabled={disabled || loading}
      data-variant={variant}
      data-size={size}
      {...props}
    >
      {loading ? '처리 중…' : children}
    </button>
  );
}
```

코드 블록에는 다음을 함께 설명한다.

- 파일 위치
- 왜 이 구조를 선택했는지
- 폐쇄망에서 어떤 부분을 직접 조립해야 하는지
- PKT 화면에서 실제로 어떻게 호출하는지

## 7. 폐쇄망 기준

외부 CDN, 런타임 원격 import, 온라인 전용 아이콘·폰트에 의존하지 않는다.

문서에는 다음 내용을 명시한다.

```text
- 사용하는 React API
- 사용하는 CSS 또는 내부 UI 유틸리티
- 외부 패키지 의존 여부
- 폐쇄망에서 대체하거나 직접 구현할 부분
```

## 8. PKT 적용 설명 기준

단순한 UI 예제에서 끝내지 말고 MES 업무 흐름과 연결한다.

예를 들어 Button 문서에는 다음을 설명한다.

```text
- 제품 등록 저장 버튼
- LOT 실행 시작 버튼
- 검사 결과 승인 버튼
- 비활성화 및 처리 중 상태
- 권한이 없는 사용자의 버튼 노출 정책
```

## 9. 작성 전 확인 목록

- [ ] 기존 1차 영역과 2차 주제가 있는지 검색했는가?
- [ ] 같은 컴포넌트의 문서를 중복 생성하지 않았는가?
- [ ] 제목만 보고 문서 목적을 알 수 있는가?
- [ ] 코드가 코드 블록으로 저장되었는가?
- [ ] 일반 본문은 문장마다 끊지 않고 문단 단위로 작성했으며, 순서·체크 항목은 하나의 목록으로 묶었는가?
- [ ] Props, 상태, 예외 상태를 설명했는가?
- [ ] 폐쇄망에서 필요한 조립 과정을 설명했는가?
- [ ] PKT MES 실제 화면과 연결했는가?
- [ ] 테스트 체크리스트를 남겼는가?
- [ ] 기존 트리에서 Category·Topic·Document ID를 먼저 확인했는가?
- [ ] 새 2차 주제와 기존 문서의 하위 문서를 혼동하지 않았는가?
- [ ] 저장 후 `parentId`, `version`, 코드 줄바꿈을 다시 조회했는가?
- [ ] 하위 문서의 `orderIdx`가 실제 실습 순서와 일치하는가? 기본 테이블은 `컴포넌트 만들기 → 페이지에 적용 → 문법 포인트` 순서인가?
- [ ] TODO 계획은 상위 본문에 있고, 하위 문서 하나가 TODO 하나를 담당하는가?
- [ ] 각 TODO 하위 문서 본문 안에 Step 1~N이 순서대로 작성되어 있는가?
- [ ] TODO와 Step 개수가 작업 범위에 맞고 인위적으로 쪼개지지 않았는가?
- [ ] 각 TODO가 하나의 결과물을 가지며, 각 Step이 하나의 구체적인 작업 단위를 다루는가?
- [ ] 구현 전 문서에 확정되지 않은 API·응답·파일 경로를 단정하지 않았는가?
- [ ] 구현 완료 Step에 실제 변경 파일, 검증 결과, 다음 단계의 전제 조건을 기록했는가?
- [ ] 구현 완료 Step마다 실제 파일 경로와 실제 코드 블록을 기록했는가?
- [ ] 계획 단계에서 존재하지 않는 파일과 코드를 임의로 만들지 않았는가?

## 10. 앱과 DB의 저장 규칙

문서는 `playbook_documents.content`에 Lexical 직렬화 JSON으로 저장된다. 직접 DB에 넣을 때는 임의의 Markdown 문자열을 넣지 말고, 앱 편집기에서 생성한 Lexical JSON 형식을 사용한다.

권장 방법은 다음과 같다.

1. 앱에서 문서를 생성한다.
2. 편집기에서 제목과 본문을 작성한다.
3. 코드 블록 도구로 코드를 입력한다.
4. 저장 버튼으로 서버에 저장한다.

DB를 직접 보정해야 한다면 `root.children` 배열, `root` 노드, 코드 블록의 `language` 필드를 포함한 유효한 Lexical JSON인지 먼저 검증한다.

## 11. 코드 블록 저장 형식의 필수 규칙

코드 블록이 빈 박스로 렌더링되지 않도록 코드 원문을 `code` 노드의 직접 필드에 넣지 않는다. 반드시 `children` 안에 `code-highlight` 자식 노드를 만들고, 실제 원문은 자식의 `text`에 넣는다.

```json
{
  "type": "code",
  "version": 1,
  "language": "tsx",
  "theme": null,
  "direction": null,
  "format": "",
  "indent": 0,
  "children": [
    {
      "type": "code-highlight",
      "version": 1,
      "detail": 0,
      "format": 0,
      "mode": "normal",
      "style": "",
      "text": "export function Example() {\n  return <div />;\n}"
    }
  ]
}
```

잘못된 형식:

```json
{"type":"code","language":"tsx","children":[],"code":"..."}
```

`children: []` 또는 `code` 직접 필드는 화면에서 빈 코드 블록을 만들 수 있다. LLM·스크립트로 저장할 때는 저장 전에 코드 노드마다 `children.length > 0`과 `children[*].type === "code-highlight"`를 검사한다. 수정 후에는 문서 상세 API를 다시 조회해 코드 자식의 `text`가 남아 있는지 확인한다.

## 11. 하위 문서 관계와 줄바꿈 전송

하위 문서는 제목만 비슷하게 만드는 것이 아니라 문서의 `parentId`가 부모 문서 ID를 가리켜야 한다. 생성 후 트리 조회에서 하위 문서의 `parentId`가 부모 ID로 표시되는지 확인한다. 본문 수정 API에서 `parentId`를 생략하면 기존 부모를 유지한다.

JSON 요청의 코드 문자열은 클라이언트가 줄바꿈을 JSON 규칙에 맞게 직렬화한다. 작성자가 코드마다 문자 `\\n`을 직접 입력할 필요는 없다. 전송 JSON에는 `\n` escape가 들어가더라도 서버가 파싱한 뒤 Lexical `code-highlight.text`에는 실제 줄바꿈이 들어가야 하며, `\\n`이 그대로 보이면 이중 escape된 잘못된 데이터다.

## 12. LLM API 작성 순서

LLM이 문서를 추가할 때는 검색창 옆 `API for LLM` 버튼의 최신 base URL과 요청 예시를 사용한다. 사용자 안내에 적힌 `topicId`나 저장소 문서의 예시 ID를 실제 위치로 간주하지 않는다. 화면에서 선택한 1차 영역·2차 주제와 `tree` 조회 결과가 일치하는지 먼저 확인한다.

```text
기존 트리 조회
→ 화면의 Category·Topic과 API 응답의 ID 일치 여부 확인
→ 없을 때만 현재 API 안내에 따른 구조 생성 호출
→ 최상위 실습 문서 생성
→ GET으로 version 확인
→ 본문 PATCH
→ 하위 문서 POST(parentId 지정)
→ 하위 문서 reorder API로 표시 순서 지정
→ tree·document GET으로 위치와 렌더링 검증
```

2차 Topic과 하위 Document는 서로 다른 개념이다. 학습 단계를 하나의 실습 문서 아래에 묶으려면 하위 문서 생성 API를 사용하고, 독립적인 주제라서 왼쪽 2차 메뉴에 보여야 할 때만 Topic을 추가한다.

본문 PATCH에는 최신 `expectedVersion`을 넣는다. 버전 충돌 응답이 오면 기존 내용을 덮어쓰지 말고 최신 문서를 다시 조회해 변경 내용을 병합한다. `content`는 일반 Markdown이 아니라 JSON으로 직렬화한 Lexical 문자열이며, 저장 후 API 응답과 앱 화면을 모두 확인한다.

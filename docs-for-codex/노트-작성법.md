# MES 학습 노트 작성법

이 문서는 `pkt-study-tauri`의 개발 학습 노트를 작성할 때 참고하는 기준 문서다.

앱의 노트 구조는 다음 3단계로 유지한다.

```text
1차 영역(Category)
└── 2차 주제(Topic)
    └── 문서(Document)
```

## 1. 1차 영역 작성 기준

1차 영역은 기술 또는 학습 목적이 크게 달라지는 단위로 나눈다. 너무 많은 영역을 만들지 말고, 관련 주제가 3개 이상 쌓일 때 분리한다.

현재 Component Recipes의 기본 영역은 다음과 같다.

```text
기본 컴포넌트
```

향후 필요할 때만 다음과 같이 영역을 추가한다.

```text
컴포넌트 조합
MES 업무 화면
폐쇄망 운영
```

## 2. 2차 주제 작성 기준

2차 주제는 실제로 재사용할 컴포넌트 하나 또는 밀접한 컴포넌트 묶음으로 만든다.

좋은 예:

```text
기본 컴포넌트
├── Button
├── Input
├── Select
├── Checkbox·Radio·Switch
├── Modal·Drawer
├── Table
├── Badge·Status
├── Tabs·Pagination
├── Loading·Empty·Error
└── Layout·Toolbar
```

피해야 할 예:

```text
기본 컴포넌트 모음
프론트엔드 이것저것
컴포넌트 관련 참고사항
```

범위가 너무 넓은 이름은 문서가 쌓일수록 찾기 어려워진다.

## 3. 문서 제목 작성 기준

하나의 문서는 하나의 학습 또는 구현 목적만 다룬다. 제목만 보아도 문서의 결과물을 알 수 있어야 한다.

권장 제목 형식:

```text
[컴포넌트명] 제조법 — [핵심 목적]
[컴포넌트명] Props와 상태 설계
[컴포넌트명] PKT 적용 예시
[컴포넌트명] 테스트 체크리스트
```

Button 예시:

```text
Button 컴포넌트 제조법 — 폐쇄망 조립형
Button Props와 상태 설계
Button PKT MES 적용 예시
Button 테스트 체크리스트
```

## 4. 컴포넌트 문서의 본문 순서

컴포넌트 문서는 아래 순서를 기본 템플릿으로 사용한다.

1. 목적
2. 사용 시나리오
3. 설계 규칙
4. Props와 상태
5. 코드 블록
6. PKT MES 적용 방법
7. 테스트 체크리스트
8. 확장 또는 주의사항

짧은 문서라도 최소한 목적, 설계 규칙, 코드 블록은 포함한다.

### 본문 줄바꿈과 화면 가독성

일반 설명 문장은 문장마다 임의로 줄을 바꾸지 않고, 화면 너비에 따라 자연스럽게 흐르도록 작성한다. 문장 사이의 강제 줄바꿈을 줄이면 넓은 화면에서 내용이 끊기지 않고 한눈에 읽힌다. 섹션 제목은 배경 없는 제목으로 두고, 제목에 속한 본문 paragraph·list 전체는 하나의 quote 배경으로 묶으며, 코드 블록은 별도 코드 박스로 표시한다.

다음 기준을 적용한다.

- 하나의 생각은 하나의 문단으로 묶고, 문장마다 줄바꿈하지 않는다.
- Lexical root는 children, direction, format, indent, type: "root", version을 포함한다.
- 새로운 주제·단계·조건으로 넘어갈 때 소제목을 사용한다. Lexical에서는 `heading` 노드 다음에 제목에 속한 본문 paragraph·list 전체를 하나의 `quote` 노드로 묶고, 파일 경로·코드는 quote 밖의 독립 `code` 블록으로 배치한다. 다음 섹션 전에는 `children: []`인 빈 paragraph 2개를 둔다.
- 순서·비교·체크 항목처럼 구조가 중요한 내용은 하나의 `list` 노드 안에 `listitem`을 묶어 작성한다. 목록 항목 사이에는 빈 paragraph를 넣지 않는다.
- 섹션 사이의 의도적인 호흡은 항상 `children: []`인 빈 paragraph 2개로 표현하며 CSS 여백에 의존하지 않는다.
- 코드, JSON, 명령어, 파일 경로처럼 줄바꿈 자체가 의미를 갖는 내용은 코드 블록 안에서 원래 줄 구조를 유지한다.
- 코드 블록은 type: "code"이며 children 안에 type: "code-highlight" 노드를 둔다. 실제 코드 전체는 해당 노드의 text에 넣고 language는 `code-highlight.text`로 지정한다.
- 본문을 한 줄로 붙이는 것은 전송용 문자열을 만들 때의 규칙이 아니라 화면에 표시되는 학습 문서의 규칙과 구분한다.

## 5. 코드 블록 작성 기준

코드는 본문에 일반 텍스트로 붙이지 말고 반드시 편집기의 코드 블록으로 작성한다.

```tsx
type ButtonVariant = 'primary' | 'secondary' | 'ghost' | 'danger';
type ButtonSize = 'sm' | 'md' | 'lg';

type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: ButtonVariant;
  size?: ButtonSize;
  loading?: boolean;
  children: React.ReactNode;
};

export function Button({
  variant = 'primary',
  size = 'md',
  loading = false,
  disabled,
  children,
  ...props
}: ButtonProps) {
  return (
    <button
      type="button"
      disabled={disabled || loading}
      data-variant={variant}
      data-size={size}
      {...props}
    >
      {loading ? '처리 중…' : children}
    </button>
  );
}
```

코드 블록에는 다음을 함께 설명한다.

- 파일 위치
- 왜 이 구조를 선택했는지
- 폐쇄망에서 어떤 부분을 직접 조립해야 하는지
- PKT 화면에서 실제로 어떻게 호출하는지

## 6. 폐쇄망 기준

외부 CDN, 런타임 원격 import, 온라인 전용 아이콘·폰트에 의존하지 않는다.

문서에는 다음 내용을 명시한다.

```text
- 사용하는 React API
- 사용하는 CSS 또는 내부 UI 유틸리티
- 외부 패키지 의존 여부
- 폐쇄망에서 대체하거나 직접 구현할 부분
```

## 7. PKT 적용 설명 기준

단순한 UI 예제에서 끝내지 말고 MES 업무 흐름과 연결한다.

예를 들어 Button 문서에는 다음을 설명한다.

```text
- 제품 등록 저장 버튼
- LOT 실행 시작 버튼
- 검사 결과 승인 버튼
- 비활성화 및 처리 중 상태
- 권한이 없는 사용자의 버튼 노출 정책
```

## 8. 작성 전 확인 목록

- [ ] 기존 1차 영역과 2차 주제가 있는지 검색했는가?
- [ ] 같은 컴포넌트의 문서를 중복 생성하지 않았는가?
- [ ] 제목만 보고 문서 목적을 알 수 있는가?
- [ ] 코드가 코드 블록으로 저장되었는가?
- [ ] 일반 본문은 문장마다 끊지 않고 문단 단위로 작성했으며, 순서·체크 항목은 하나의 목록으로 묶었는가?
- [ ] Props, 상태, 예외 상태를 설명했는가?
- [ ] 폐쇄망에서 필요한 조립 과정을 설명했는가?
- [ ] PKT MES 실제 화면과 연결했는가?
- [ ] 테스트 체크리스트를 남겼는가?
- [ ] 기존 트리에서 Category·Topic·Document ID를 먼저 확인했는가?
- [ ] 새 2차 주제와 기존 문서의 하위 문서를 혼동하지 않았는가?
- [ ] 저장 후 `parentId`, `version`, 코드 줄바꿈을 다시 조회했는가?
- [ ] 하위 문서의 `orderIdx`가 실제 실습 순서와 일치하는가? 기본 테이블은 `컴포넌트 만들기 → 페이지에 적용 → 문법 포인트` 순서인가?

## 9. 앱과 DB의 저장 규칙

문서는 `playbook_documents.content`에 Lexical 직렬화 JSON으로 저장된다. 직접 DB에 넣을 때는 임의의 Markdown 문자열을 넣지 말고, 앱 편집기에서 생성한 Lexical JSON 형식을 사용한다.

권장 방법은 다음과 같다.

1. 앱에서 문서를 생성한다.
2. 편집기에서 제목과 본문을 작성한다.
3. 코드 블록 도구로 코드를 입력한다.
4. 저장 버튼으로 서버에 저장한다.

DB를 직접 보정해야 한다면 `root.children` 배열, `root` 노드, 코드 블록의 `language` 필드를 포함한 유효한 Lexical JSON인지 먼저 검증한다.

## 10. 코드 블록 저장 형식의 필수 규칙

코드 블록이 빈 박스로 렌더링되지 않도록 코드 원문을 `code` 노드의 직접 필드에 넣지 않는다. 반드시 `children` 안에 `code-highlight` 자식 노드를 만들고, 실제 원문은 자식의 `text`에 넣는다.

```json
{
  "type": "code",
  "version": 1,
  "language": "tsx",
  "theme": null,
  "direction": null,
  "format": "",
  "indent": 0,
  "children": [
    {
      "type": "code-highlight",
      "version": 1,
      "detail": 0,
      "format": 0,
      "mode": "normal",
      "style": "",
      "text": "export function Example() {\n  return <div />;\n}"
    }
  ]
}
```

잘못된 형식:

```json
{"type":"code","language":"tsx","children":[],"code":"..."}
```

`children: []` 또는 `code` 직접 필드는 화면에서 빈 코드 블록을 만들 수 있다. LLM·스크립트로 저장할 때는 저장 전에 코드 노드마다 `children.length > 0`과 `children[*].type === "code-highlight"`를 검사한다. 수정 후에는 문서 상세 API를 다시 조회해 코드 자식의 `text`가 남아 있는지 확인한다.

## 11. 하위 문서 관계와 줄바꿈 전송

하위 문서는 제목만 비슷하게 만드는 것이 아니라 문서의 `parentId`가 부모 문서 ID를 가리켜야 한다. 생성 후 트리 조회에서 하위 문서의 `parentId`가 부모 ID로 표시되는지 확인한다. 본문 수정 API에서 `parentId`를 생략하면 기존 부모를 유지한다.

JSON 요청의 코드 문자열은 클라이언트가 줄바꿈을 JSON 규칙에 맞게 직렬화한다. 작성자가 코드마다 문자 `\\n`을 직접 입력할 필요는 없다. 전송 JSON에는 `\n` escape가 들어가더라도 서버가 파싱한 뒤 Lexical `code-highlight.text`에는 실제 줄바꿈이 들어가야 하며, `\\n`이 그대로 보이면 이중 escape된 잘못된 데이터다.

## 12. LLM API 작성 순서

LLM이 문서를 추가할 때는 검색창 옆 `API for LLM` 버튼의 최신 예시를 사용한다. `structure`를 기존 트리에 반복 호출하면 같은 1차·2차 메뉴가 중복될 수 있으므로, 항상 먼저 `tree`를 조회한다.

```text
기존 트리 조회
→ 필요한 Category·Topic·Document ID 확인
→ 없을 때만 structure 호출
→ 최상위 실습 문서 생성
→ GET으로 version 확인
→ 본문 PATCH
→ 하위 문서 POST(parentId 지정)
→ 하위 문서 reorder API로 표시 순서 지정
→ tree·document GET으로 위치와 렌더링 검증
```

2차 Topic과 하위 Document는 서로 다른 개념이다. 학습 단계를 하나의 실습 문서 아래에 묶으려면 하위 문서 생성 API를 사용하고, 독립적인 주제라서 왼쪽 2차 메뉴에 보여야 할 때만 Topic을 추가한다.

본문 PATCH에는 최신 `expectedVersion`을 넣는다. 버전 충돌 응답이 오면 기존 내용을 덮어쓰지 말고 최신 문서를 다시 조회해 변경 내용을 병합한다. `content`는 일반 Markdown이 아니라 JSON으로 직렬화한 Lexical 문자열이며, 저장 후 API 응답과 앱 화면을 모두 확인한다.
